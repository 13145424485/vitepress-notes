**1. 为什么 RAG 要先 ensureIndexed(postId)？**

可以这样答：

“因为问答接口依赖向量索引，如果索引不存在、过期或者正文更新了但索引没更新，后面的检索结果就不可靠了。所以我在问答入口先做一次 ensureIndexed(postId)，本质上是一个轻量兜底。这样能保证用户第一次提问时也能拿到可用结果，而不是因为离线索引没跑成功直接查不到。”

展开一点：

“我这里不是每次都全量重建，而是先做存在性和指纹判断，比如 content 的 hash 或 etag 没变就跳过；变了才删除旧分块再重建。这样兼顾可用性和性能。”

如果面试官继续问“为什么不完全异步”：

“可以异步，但纯异步会有窗口期。我的做法是发布时预索引，问答时再兜底一次，这样用户体验更稳。”

**2. 为什么向量检索后还要按 postId 过滤？**

“因为我的场景是单篇知文问答，不是全库问答。向量检索本身只负责找语义相似内容，它可能把别的文章里语义相近的 chunk 也召回。如果不按 postId 过滤，模型会拿到跨文章上下文，答案就可能‘串文’。”

再补一句：

“所以我一般是先扩大召回，再按 metadata.postId 做服务端过滤，最后取 topK。这样既保证召回率，又保证答案严格限定在当前文章上下文内。”

**3. 为什么分块要 800 + 100 overlap？**

“这个是一个工程上的折中值，不是绝对标准。800 字符左右能保证每块语义相对完整，又不会太大到浪费 token；100 字符 overlap 是为了避免关键信息刚好落在两个 chunk 边界，导致上下文断裂。”

进一步展开：

“如果块太小，语义碎，召回噪声会高；如果块太大，embedding 粒度太粗，而且 prompt 成本上升。overlap 的作用是保连续性，尤其对问答、摘要、定义解释这种任务很有用。”

如果被问“为什么不是 500 或 1000”：

“这个需要结合正文长度、段落结构、模型上下文窗口和实际评估去调。800+100 不是理论最优，是我在当前文章型内容里比较稳的经验值。”

**4. 为什么流式输出你用了 WebSocket / SSE？**

“如果是我简历里的知文问答接口，我更偏向用 SSE。因为这是典型的服务端单向持续输出场景，前端发一个问题，后端持续把模型生成的文本往前推，SSE 在协议层就很适合，基于 HTTP，接入简单，和 WebFlux 也比较顺。”

“如果是我实习里做的智能问答流式输出，我用了 WebSocket，因为当时不仅要服务端推流，还要处理一些交互状态，比如连接管理、前端消息控制、可能的中断或多轮互动，WebSocket 更灵活。”



“SSE 更适合单向文本流，简单、轻量、天然支持 HTTP 语义；WebSocket 更适合双向实时通信，但实现和维护复杂度更高。我的原则是能用 SSE 解决就不用 WebSocket，除非业务确实需要双向交互。”

**5. 为什么 Redis 计数不用直接查库？**

“因为点赞、收藏、关注这类计数是高频读写场景，直接打 MySQL 会把数据库变成热点，写放大和锁竞争都会比较严重。Redis 更适合承接这种高并发计数。”



“我的做法一般是 Redis 承接实时计数，数据库做最终持久化或异步汇总。这样能把读写延迟降下来，同时把主库保护住。”

如果追问一致性：

“这类场景通常**接受最终一致性**，不一定追求强一致。关键是保证幂等、原子更新，以及异常情况下有重建机制。”

**6. 为什么秒杀要 Lua + Redis Stream + 分布式锁？**

“这是分层解决问题。Lua 脚本负责把库存扣减和一人一单校验做成原子操作，先把最核心的并发冲突挡在 Redis 层；Redis Stream 负责异步削峰，把下单请求和数据库写入解耦；分布式锁是进一步保护用户维度或业务关键区，避免并发下重复下单或者并发覆盖。”

更像面试的表达：

“如果只用锁，不够快；只用消息队列，不足以在入口快速失败；只用 Redis 扣库存，又缺少后续异步落库和失败补偿。所以这几个组件是组合使用，不是互相替代。”

**7. 为什么 Elasticsearch 用 search_after 而不是 from + size？**

“因为 from + size 深分页性能会越来越差，ES 需要先取出前面大量结果再丢弃，代价很高。search_after 是基于上一页最后一条排序值继续往后翻，更适合深分页和滚动浏览。”

继续补：

“我的搜索场景如果是 Feed 流或连续翻页，search_after 更稳定；from + size 更适合前几页、页码跳转明确的小分页。”

**8. DeepSeek 接口慢在哪里，你是怎么降 65% 的？**

这个问题千万别瞎编，要按“测量口径 + 优化动作 + 结果”答。

“慢主要有几个来源：模型本身推理延迟、重复问题导致的重复调用、请求高峰时多个相似请求同时打模型、还有前端必须等完整结果返回才能展示。我当时做的优化重点不是改模型内部，而是做调用层和交互层优化。”

然后分点说：

“第一，请求合并。对于短时间内重复或相近的请求，避免并发重复打模型。”
“第二，缓存。对可复用结果做缓存，减少命中模型的次数。”
“第三，流式输出。不是等模型全部生成完再返回，而是边生成边推给前端，优化首字节时间和用户体感。”
“第四，控制 prompt 大小和 maxTokens，减少不必要的生成开销。”

**二、Python 相关高频问题怎么答**

**9. Python 的 list 和 tuple 区别？**

“最核心区别是可变和不可变。list 可变，适合动态增删改；tuple 不可变，更适合表达固定结构的数据。不可变对象通常也更适合作为 dict 的 key，前提是里面元素本身也可哈希。”

**10. deepcopy 和浅拷贝区别？**

“浅拷贝只拷贝最外层对象，内部嵌套对象还是共享引用；深拷贝会递归复制整个对象结构，互不影响。业务里如果只是简单容器复制，用浅拷贝就够；如果涉及嵌套对象独立修改，才需要深拷贝，因为深拷贝成本更高。”

**11. \*args 和 \**kwargs 是什么？**

“*args 接收位置参数，打包成 tuple；**kwargs 接收关键字参数，打包成 dict。常见场景是写通用函数、装饰器或者做参数透传。”

**12. 装饰器是什么，什么时候用？**

“装饰器本质上是对函数或方法做一层包装，在不改原函数代码的前提下增强功能。比如日志、鉴权、耗时统计、重试、缓存，这些横切逻辑很适合装饰器。”

**13. 生成器和迭代器区别？**

“迭代器是实现了迭代协议的对象，有 __iter__ 和 __next__；生成器是一种特殊的迭代器，通常由 yield 生成。生成器最大的好处是惰性求值，更省内存，适合流式处理和大数据量遍历。”

**14. GIL 是什么？**

“GIL 是 CPython 的全局解释器锁，意味着同一时刻只有一个线程执行 Python 字节码。所以 CPU 密集型任务多线程收益有限，I/O 密集型任务多线程和协程依然有价值。”

**15. 多线程、多进程、协程分别适合什么？**

“CPU 密集型更适合多进程，绕开 GIL；I/O 密集型适合多线程或协程；高并发网络请求场景下协程通常更轻量。选型关键看瓶颈是 CPU 还是 I/O。”

**16. FastAPI 怎么定义一个 RESTful 接口？**

“我会先定义路由和请求模型，比如用 Pydantic 做参数校验；返回统一响应结构；异常通过全局异常处理器收敛；日志里打 requestId；鉴权一般放到依赖注入或中间件里。”

你可以顺手说个例子：

“比如问答接口我会定义 POST /api/v1/qa 或 GET /api/v1/posts/{id}/qa/stream，前者适合普通问答，后者适合流式问答。”

**17. 如何处理参数校验、异常、日志、鉴权？**

“参数校验交给 Pydantic；异常分业务异常和系统异常，统一映射成标准状态码和错误码；日志至少记录请求参数摘要、耗时、异常堆栈和 traceId；鉴权一般是 JWT + 中间件或依赖注入。”

**三、Web 后端 / RESTful 高频问题**

**18. 你怎么设计一个问答接口？**

“如果是非流式，我会用 POST /api/v1/qa，body 里放 postId、question、topK、maxTokens。如果是流式回答，我更倾向 GET /api/v1/posts/{id}/qa/stream?question=...，响应类型是 text/event-stream。”

“接口设计上要考虑参数校验、鉴权、限流、超时、traceId、错误兜底、是否记录问答日志，以及能不能取消生成。”

**19. SSE 和 WebSocket 区别？**

“SSE 是服务端到客户端单向流，基于 HTTP，适合消息推送和模型流式文本输出；WebSocket 是双向全双工，适合聊天室、协同编辑、实时互动。对大模型逐字返回这种场景，SSE 更轻，WebSocket 更通用。”

**20. JWT 刷新机制怎么设计？**

“我一般会设计 access token + refresh token 双令牌。access token 短期有效，refresh token 周期更长。access token 过期后，通过 refresh token 换新 access token。关键点是 refresh token 要支持撤销、轮换和风控，比如登出后失效，多设备策略要明确。”

**21. 如何保证接口幂等？**

“看场景。创建类请求一般会引入幂等键，比如订单号、请求唯一 ID；更新类请求可以靠版本号或状态机约束；像秒杀和支付场景还要结合 Redis 或数据库唯一约束兜底。幂等不是只靠 HTTP 方法语义，而是靠业务主键和状态设计。”

**22. 如果一个接口很慢，你怎么排查？**

“我一般按链路拆：入口耗时、业务逻辑耗时、数据库、缓存、RPC、第三方接口。先看日志和 trace，再看监控指标，比如 QPS、RT、错误率、慢 SQL、线程池、GC、下游超时。如果是 AI 问答接口，还要拆 prompt 构造、检索耗时、模型调用耗时、流式首 token 时间。”

**23. AI 接口超时或返回错误怎么办？**

“要做超时控制、重试策略和降级。超时不能无限等；重试只对幂等场景做，而且要限次数；降级可以返回‘当前繁忙，请稍后重试’，或者走简化回答路径。日志里必须把模型请求 id、超时、错误码打出来，便于排查。”

**24. 用户频繁发问，如何限流？**

“可以按用户、IP、文章维度做限流。实现上常见是 Redis + 滑动窗口或令牌桶。高成本接口，比如模型调用，我会同时加并发数限制和速率限制，避免某个用户把模型资源打满。”

**四、RAG / LLM / Agent 高频问题**

**25. 为什么需要 RAG，不直接把问题丢给模型？**

“因为通用模型没有你业务私有知识，或者知识不实时、不准确。直接问模型容易幻觉。RAG 的作用是**先检索到业务相关上下文，再让模型基于这些上下文回答**，本质上是把‘记忆问题’转换成‘检索+生成问题’。”

**26. embedding 模型怎么选？**

“我看三个点：语义效果、成本、延迟。中文场景优先看中文语义表现；线上还要考虑向量维度、调用成本、吞吐和部署方式。如果是业务初期，我会先选稳定、通用的 embedding 模型，效果不够再做 AB 测试和替换。”

**27. topK 怎么定？**

“topK 不是越大越好。太小可能漏信息，太大容易引入噪声，还会增加 token 成本。我的做法一般是先扩大召回，比如先取 20，再过滤，再取最终 topK，比如 3 到 5，结合离线评估和线上问答效果去调。”

**28. 如何降低幻觉？**

“主要是三层。第一，检索层提高召回质量，减少错召回。第二，Prompt 层明确要求只基于上下文回答，不确定就说不确定。第三，结果层做引用来源、答案约束甚至二次校验。核心原则就是减少模型‘自由发挥’空间。”

**29. 如何处理文档更新？**

“要做幂等和增量更新。常见是给正文做 hash 或 etag，未变更就跳过；变更了先删除旧 chunk，再重建向量索引。否则最容易出现旧内容和新内容并存，模型读到脏上下文。”

**31. 如何评估 RAG 效果？**

“我会看三类指标。检索质量，比如命中率、召回率；回答质量，比如准确性、完整性、是否幻觉；工程指标，比如延迟、token 成本、首 token 时间。更实际一点，就是准备一批标准问答集做离线评测，再结合线上用户反馈。”

**32. Spring AI 为什么不用 LangChain？**

“因为我的主技术栈是 Java，项目本身也是 Spring 体系。用 Spring AI 的好处是和现有 Spring Boot、配置体系、依赖注入、监控链路更自然地融合，工程接入成本低。LangChain 在 Python 生态更丰富，如果整个项目是 Python 技术栈，我会更倾向 LangChain 或 LangGraph。”

这个回答很稳，因为不是踩一捧一。

**33. Agent 和普通问答的区别？**

“普通问答通常是单轮输入到输出，最多带检索上下文；Agent 更强调多步推理、工具调用和任务执行。比如查天气、再订票、再发通知，这种需要规划和外部系统交互的更像 Agent，不只是回答问题。”

**34. function calling / tool calling 是什么？**

“就是让模型不是直接输出自然语言，而是根据 schema 决定什么时候调用外部工具，比如搜索、数据库查询、发邮件、调用内部 API。模型负责决策，系统负责真正执行工具，再把结果回填给模型。”

**35. 如果让你做一个 AI Agent，你会怎么设计？**

“我不会一开始就做全自治 Agent。真实业务里我会先把任务拆成可控流程：意图识别、工具选择、参数补全、执行、结果回填。如果任务路径比较固定，我更倾向‘工具调用 + 状态机’，可观测、可回放、可兜底；只有多步决策明显复杂时，才考虑引入 ReAct 或 LangGraph 这一类编排方式。”

**五、数据库 / Redis / MQ / ES 高频问题**

**36. Redis 计数系统怎么保证一致性？**

“我不会说绝对强一致，而是说最终一致。入口用 Redis 承接高频写，Lua 脚本保证原子更新；读路径优先走 Redis；异常时通过校验任务或重建机制修复。关键是业务要接受短时不一致，但要保证趋势正确和最终收敛。”

**37. 秒杀怎么防超卖？**

“核心是三层。第一层 Redis 预扣库存，入口快速失败；第二层 Lua 保证库存扣减和一人一单原子执行；第三层异步下单时结合数据库约束和锁，保证最终订单一致性。超卖往往不是单点问题，而是多个环节并发失控，所以要分层兜底。”

**38. Lua 为什么原子？**

“因为 Redis 执行 Lua 脚本时是单线程串行执行，脚本中的多个操作在执行期间不会被别的命令打断，所以能把多个 Redis 操作合并成一个原子单元。”

**39. Redis Stream、消费组、pending-list 是什么？**

“Redis Stream 可以理解成消息流结构。消费组支持多消费者协作消费；pending-list 记录已投递但未 ack 的消息，方便失败重试和故障恢复。这也是我在异步下单场景里用它的原因，能比简单 list 更好地处理消费确认和重试。”

**40. MQ 的消息重复、丢失、积压怎么处理？**

“重复靠消费幂等，比如业务唯一键、去重表、状态机；丢失要看生产端确认、Broker 持久化和消费端 ack 机制；积压一般靠扩容消费者、限流上游、降级非核心消息以及排查慢消费原因。”

**41. ES 搜索怎么和向量检索结合？**

“如果是关键词明确的场景，用 ES 关键词检索和 BM25 很有效；如果是语义表达不一致但意思接近的场景，向量检索更好。工程上可以做混合检索：先用关键词和语义双路召回，再融合排序，或者用 metadata 过滤后再向量检索。”

**42. function_score 是干什么的？**

“它是在文本相关性分数基础上，再融合业务分，比如热度、点赞数、时间衰减等。这样结果不只是‘文本像’，还更符合业务排序目标。”

**六、Linux / 工程化 高频问题**

**43. 线上服务挂了你怎么查？**

“先确认范围，是单机、单接口还是整体服务。然后看进程是否存活、端口是否监听、日志有没有报错、CPU/内存/磁盘是否异常、下游依赖是否超时。再根据 trace 和监控定位是应用层异常、数据库慢、缓存击穿还是外部依赖故障。”

**44. 日志怎么实时看？**

“最直接是 tail -f，需要过滤就配合 grep 或 rg。如果是容器环境，我会用 docker logs -f。线上一般还会结合日志平台按 traceId 或关键字查。”

**45. 怎么看某端口被谁占用？**

“Linux 下可以用 ss -lntp 或 netstat -lntp，再结合 lsof -i:端口 看具体进程。”

**46. 怎么验证一个接口通不通？**

“最常用是 curl，看状态码、响应头、耗时。如果要测 HTTPS、鉴权、超时、header 这些，也都可以直接用 curl 模拟。内网接口不通时还要结合 DNS、端口连通性和网关规则去看。”

**47. 怎么部署一个 Python / Java 服务？**

“最简单是打包后用 systemd 或脚本启动；更标准是 Docker 化部署，配置环境变量、日志目录、端口、健康检查。Java 一般是 jar 或容器，Python 一般是 uvicorn/gunicorn + FastAPI/Flask，再配 nginx 或网关。”

**七、前端 / 全栈 高频问题**

**48. 前端如何消费 SSE 或 WebSocket？**

“SSE 前端一般直接用 EventSource，监听 message、error，收到分片就拼接到页面状态里。WebSocket 则是建立 socket 连接，自己定义消息协议和状态。对问答场景，前端核心是增量渲染、错误处理和取消机制。”

**49. 如果要做一个问答页，页面状态怎么管理？**

“我会把状态拆成输入区、会话列表、当前流式回答、加载状态、错误状态、连接状态。流式输出时把新的 token 或片段 append 到当前回答里，不要整段重渲染。取消时要终止连接并把当前状态置为中断。”

**50. 如何处理中断、重试、取消回答？**

“取消回答本质是前端断开 SSE/WebSocket，后端也要感知连接关闭；重试要注意幂等和上下文恢复；中断后的 UI 要明确告诉用户‘回答已停止’，不要让用户误以为模型卡死。”

**八、如果面试官直接追着问你“Python 重写”和“Agent 设计”**

**51. 如果让你现在用 Python 重写这个问答服务，你会怎么做？**

“我会用 FastAPI 做接口层，问答流式输出用 StreamingResponse 或 SSE；文档索引做成独立服务或后台任务；embedding 和 LLM 调用用统一 client 封装；向量存储可以继续用 Elasticsearch，也可以用 pgvector/Milvus 这类更专门的向量库，取决于团队现有栈；鉴权、日志、trace、限流这些还是按照标准 Web 服务去做。”

“如果追求快速落地，我会先做最小闭环：上传文档、切块、embedding、检索、prompt、流式回答。等业务跑起来，再补多租户、权限、缓存、离线评估和可观测性。”
